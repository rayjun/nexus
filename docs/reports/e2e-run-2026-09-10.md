## 3 · 抓到的缺陷与修法

### 3.1 瞬时错误被当成永久离线（已修 · `3aa58c9`）

relay 对"对端正在重连期间发出的每一条帧"都会回 `error: peer not connected`。原代码把任何 `error` 都当作"被拒绝 join"，直接 `isConnected = false`；而**没有任何路径把它翻回来**，于是握手完成后的 roster 刷新因 `!server.isOnline` 被 `continue` 跳过 → app 卡在「No bots yet」直到手动下拉刷新。

修：只有非瞬时的错误才置离线。

### 3.2 密钥无法收敛时静默挂死（已修 · `3aa58c9`）

**根因**：PSK 混入在两条路径上不对称。

| 路径 | agent (`relay_agent.py`) | app (`ServerConnection.swift`) |
|---|---|---|
| 首次配对 | `:164-170` 混 pairing code 作 PSK | `:233` 混 PSK（`pairingPSK`） |
| 重连 rekey | `:268-271` 不混 | `handleRekey` 不混 |

`--pair` 会清掉 `~/.hermes/mobile` 的密钥，于是 agent 走"首配"（混 PSK），而 Keychain 里已有密钥的 app 走 `handleRekey`（不混 PSK，且配对成功后 `pairingPSK = nil` 已丢弃）→ 双方各自"成功"派生出不同密钥，双向全解不开，RPC 一路 30s 超时。

实测（app 日志 / agent 日志同一时刻）：app `rpc sent: profiles.list id=6 seq=4` → agent `decrypt failed`；延迟重试的帧同样失败。

修（选 A：暴露 + 兜底）：对端在线且本会话见过对端公钥时，连续 2 次 RPC 超时 → 标记 server 需重配（`isConnected = false`，roster 行随之显示「Offline — re-pair in Settings」，Settings → Servers 的 Re-pair 可一键清密钥重配）。**不自动删密钥**：一次超时风暴不该毁掉可能有效的配对，Re-pair 本来就会清。配套：`ChatListView` 在 `RelayPaired` 后补发一次 roster 请求，使该场景稳定产生第二次超时。

**修正一个此前的说法**：该错配不是永久的 —— app 与 agent 任一方重连后会重新走"双方都不混 PSK"的 rekey 路径，密钥重新收敛（实测 17:41 一次重连后 roster 自行恢复）。所以 (A) 覆盖的是"错配窗口内 app 无任何提示"这一段。

### 3.3 空态吞掉顶栏（已修 · `97ea516`）

`content` 在 roster 为空时直接返回 `emptyNoServers`/`emptyNoBots`，`topBar` 不渲染 → 搜索、`+`、**设置齿轮全部消失**，Settings/Servers/重配不可达，而空态文案还写着 "Tap + to create your first bot"。修：`topBar` 无条件渲染，空态挂其下。

顺带：空态标题 `No bots yet`/`No servers yet` 是标题走 `text`，解释行才走 `muted`（两档之间只差 2pt 会把层级压平）。

实测（截图 `docs/reports/shots/37-empty-state.png`）：顶栏出现（放大镜在 y≈0.11），标题取色 (46,48,56) = `text`，副标题 (98,104,116) = `muted`。

### 3.4 状态标签用色不达标（已修 · `eafba25`）与命名修正（`9e9c474`）

"Online" 是 `green` 文字 = 浅色 3.88:1 < 4.5，而同一个槽位的 "Offline" 已迁到 `muted`。规则：状态**点**保有颜色（非文字 ≥3:1 两模式都过），状态**词**一律 secondary。
`subtleText` 改名 `graphic` —— 它自己的文档写着 "NEVER use for text"，名字却叫 Text；值不变（3.47/4.78）。
